# Эксплуатация и границы версии 0.1.0

## Процессы и хранение

Один сервер Uvicorn и один встроенный поток worker. SQLite использует WAL, foreign keys и `BEGIN IMMEDIATE`: приём приглашения и подтверждения выполняются атомарно. Не использовать несколько реплик и несколько Uvicorn workers. Диск `/data` должен быть постоянным. После остановки сервера фоновые задачи останавливаются; после запуска очередь сохраняется.

`GET /health` проверяет базу и возвращает `worker_heartbeat`. Внешний монитор должен проверять не только HTTP 200, но и свежесть heartbeat (обычно раз в 15 секунд; тревога, например, после 120 секунд). Сервис не должен засыпать.

Технические настройки, выбранные для первой версии, а не новые продуктовые решения: срок сессии и свежесть initData — 1 час; случайный invite 256 бит; максимум 3 напоминания; запрос диапазона до 370 дней; лимит ZIP 10 MiB, распакованного содержимого 40 MiB; до 2000 экземпляров на развёртку; ограничение частоты 120 запросов в минуту на IP/путь. При необходимости эти значения пересматриваются после измерений.

## Очередь Telegram

Напоминания создаются на три дня вперёд. Даты считаются в зоне события; для «Весь день» — от полуночи в зоне получателя. Прошедшие точки при создании, восстановлении, переносе или отмене удаления не догоняются. Уже поставленное напоминание с опозданием более 90 секунд помечается `expired` (инженерный допуск на интервал worker, не продуктовый период напоминания).

Ключи дедупликации включают событие, исходный экземпляр, версию расписания, Telegram ID, интервал и точную дату отправки. Незапущенный бот и запрет сообщений отображаются в настройках. Telegram 400/403 прекращает попытки; retry-after и временные ошибки обрабатываются с задержкой.

В Bot API нет общего idempotency-key для sendMessage: при сетевом разрыве после фактического принятия сообщения невозможно одновременно гарантировать отсутствие дублей и гарантированную доставку. Очередь предотвращает обычные дубли и webhook replay, но это не доказательство строго exactly-once доставки. Такая редкая неопределённость должна учитываться при production review.

Выход/lock отменяют ожидающие задания. Уже принятый Telegram запрос невозможно отозвать. Действия не должны раскрывать другим пользователям токен или тело initData; access log отключён. Логи исключений не содержат Telegram URL с токеном.

## Подпись архивов и политика ключей

- При первом запуске создаётся Ed25519 private key `ARCHIVE_KEY_FILE` с правами 0600. Он не входит в ZIP.
- `ARCHIVE_PUBLIC_KEYS` хранит реестр публичных ключей по fingerprint. Подпись проверяется только по этому доверенному реестру, не по ключу из загруженного архива.
- Подписан канонический manifest с SHA-256 payload, версией формата и key ID. Payload включает ID логического календаря и исходной пары.
- Для плановой ротации остановить сервис, сохранить текущий private key защищённо, оставить старые public keys в реестре, заменить private key новым, затем запустить сервис. Новый публичный ключ добавится. Старые public keys сохранять бессрочно, пока обещана проверяемость ранее выданных ZIP.
- Резервировать базу, private key и public registry на отдельном защищённом носителе. Для проверки старых архивов нужен старый public key, для новых подписей — private key.
- Удаление календаря не удаляет серверные ключи подписи, иначе правила восстановления после полного удаления перестанут выполняться.
- Компрометация private key требует процедуры отзыва и уведомления: автоматического безопасного доверия старым архивам после компрометации не существует. Нужна операторская политика.

Данные ZIP не шифруются: это файл с личной историей, его хранение контролирует скачавший пользователь. Провайдерских OAuth-токенов/паролей в архиве нет.

## Служебная резервная копия

`python -m scripts.backup_database /path/to/secure/calendar.sqlite3` использует SQLite backup API, а не копирование открытого WAL-файла. Держать резервную копию за пределами рабочего диска. Отдельно сохранять ключи подписи. Доступ ограничивать оператором. Периодически проверять восстановление на отдельном стенде.

При восстановлении служебной БД не поднимать одновременно вторую production-копию с тем же webhook и очередью. Обычный пользовательский ZIP восстанавливается только через собственный workflow с проверкой пары.

## Защита запросов

Bearer session хранится только в памяти frontend, не в URL/localStorage. Каждая операция заново проверяет активность участника, календарь и его состояние. Revision блокирует потерю параллельных правок. Webhook требует отдельного secret header. Нет wildcard CORS. CSP ограничивает скрипты своим доменом и Telegram SDK; пользовательский HTML не исполняется.

После выхода session остаётся криптографически действительной до истечения TTL, но доступ к событиям, категориям, settings и архивам немедленно прекращается серверными проверками. Разрешены только собственный state и возвращение. HTTPS и защита секретов обеспечиваются размещением.

## Что предстоит перед релизом

Реальные iOS/Android/desktop Telegram WebView, Background bot consent, сети и retries, нагрузка, лимиты загружаемого тела на reverse proxy, политика персональных данных, автоматические encrypted operator backups, мониторинг и аварийное восстановление. Внешние интеграции пока не включены и ничего не записывают в Google/iCloud.
