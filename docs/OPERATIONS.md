# Эксплуатация Our Calendar 0.3.0

Одна реплика, один Uvicorn-процесс, SQLite WAL на постоянном `/data`. Напоминания, перевод и служебное резервное копирование работают в трёх независимых фоновых потоках. Недоступный перевод/S3 не блокирует отправку напоминаний. Несколько реплик и несколько Uvicorn workers не поддерживаются.

## Работоспособность и наблюдение

`GET /health` не раскрывает события, имена, Telegram ID или секреты. `ready` означает, что основной обработчик успешно завершал цикл в последние 120 секунд. При остановившемся обработчике HTTP-код — 503. `degraded` также учитывает недоступный/устаревший перевод и отсутствие свежей проверенной резервной копии, если соответствующий сервис настроен. Перевод проверяется синтетическими текстами в обоих направлениях каждые 5 минут; проверка старше 10 минут считается устаревшей. Копия старше 26 часов считается устаревшей. Новое развёртывание может кратковременно иметь `degraded=true` до первой проверки.

`.github/workflows/monitor.yml` проверяет `/health` каждые 15 минут и по ручному запуску. GitHub Actions может задерживать расписание; это мониторинг по возможности, без SLA и без отдельной системы оповещения. Результаты и ошибки видны в Actions. Основной healthcheck Railway проверяет `/health` при развёртывании. Сам по себе он не является постоянным watchdog. Настройки приложения показывают статус фоновых служб и последнюю успешную копию.

## Очередь Telegram

Интервалы: 24 ч, 12 ч, 2 ч, 1 ч, 30 мин, 15 мин, до трёх на человека. Уведомление о начале независимо включается пользователем и не занимает один из трёх интервалов. Главный переключатель напоминаний имеет приоритет. По умолчанию уведомление о начале включено и для старых аккаунтов.

Очередь рассчитывается на три дня вперёд. «Весь день» отсчитывается от полуночи получателя; обычные события — по IANA timezone с DST. Прошедшие точки не догоняются. Задание с опозданием более 90 секунд истекает. Перенос, статус, выход и удаление отменяют прежние задания. Дедупликация учитывает ID, экземпляр, версию расписания, получателя, интервал и дату отправки. Временные ошибки используют retry-after/backoff; 400/403 прекращают попытки и отображаются пользователю. Текущий перевод экземпляра подставляется перед отправкой напоминания.

Bot API не предоставляет общий idempotency-key для sendMessage. После сетевого разрыва уже принятого сообщения нельзя одновременно гарантировать строго однократную доставку и обязательную повторную попытку. Обычные дубли предотвращены, эта редкая неопределённость остаётся ограничением Telegram. Принятый Telegram запрос после выхода участника отозвать нельзя.

## Автоматические служебные резервные копии

Отдельное приватное хранилище `calendar-backups`, регион Railway **ams**. Ежедневно создаётся согласованный SQLite snapshot через backup API; вместе с ним сохраняются ключ подписи пользовательских ZIP и реестр публичных ключей. Полный архив шифруется Fernet до передачи по HTTPS. Ключ расшифровки хранится отдельно от диска в защищённой переменной Railway `OPERATOR_BACKUP_KEY`; в архив он не попадает.

Перед отметкой успеха файл скачивается из S3, расшифровывается и восстанавливается во временную папку. Проверяются SHA-256 файлов, SQLite integrity и foreign keys. Pending/sending сообщения в проверяемой восстановленной копии отменяются, чтобы аварийное восстановление не повторяло старые действия. Следующие будущие напоминания рассчитываются заново после запуска. При ошибке статус становится `failed`, повтор — через 15 минут. После успешной проверки удаляются объекты старше **7 дней** в собственном префиксе `our-calendar/operator/v1/`. При недоступном S3 удаление старых копий задерживается до следующего успешного цикла. Это служебные копии оператора, не пользовательская функция восстановления календаря после его полного удаления. Перед окончательным удалением календаря его ID/время удаления записываются в отдельный зашифрованный журнал `our-calendar/deletions/v1.ledger` и проверяются чтением. До подтверждения журнала календарь остаётся заблокированным; при недоступном S3 очистка задерживается. После истечения 30 дней отмена уже недоступна. Журнал не удаляется ротацией snapshots. Offline-восстановление требует актуальный журнал и исключает календари, удалённые после создания выбранной копии; легальное последующее восстановление той же пары из пользовательского ZIP этим не запрещается.

Переменные:

| Переменная | Значение |
| --- | --- |
| OPERATOR_BACKUP_ENDPOINT | `${{calendar-backups.ENDPOINT}}` |
| OPERATOR_BACKUP_BUCKET | `${{calendar-backups.BUCKET}}` |
| OPERATOR_BACKUP_REGION | `${{calendar-backups.REGION}}` |
| OPERATOR_BACKUP_ACCESS_KEY | `${{calendar-backups.ACCESS_KEY_ID}}` |
| OPERATOR_BACKUP_SECRET_KEY | `${{calendar-backups.SECRET_ACCESS_KEY}}` |
| OPERATOR_BACKUP_KEY | Случайный Fernet-ключ; не выводить в логи и не коммитить |

При утрате рабочего volume восстановление возможно, пока сохранены объект, ключ расшифровки и доступ к Railway. Утрата всего Railway-аккаунта вместе с переменными не покрывается этой схемой. Оператор должен хранить дополнительную защищённую копию ключа вне Railway. Хранилище использует оплачиваемые ресурсы Railway; отдельной постоянно работающей реплики для копирования нет.

## Аварийное восстановление

1. Остановить рабочий сервис и убедиться, что второй экземпляр с тем же ботом/очередью не запущен.
2. Скачать нужный `.ocb` и **актуальный** `our-calendar/deletions/v1.ledger` из приватного bucket через доступ оператора. Получить `OPERATOR_BACKUP_KEY` из защищённых переменных. Не вставлять ключ в командную строку или историю shell.
3. В изолированной среде задать ключ через безопасный менеджер окружения и запустить `python -m scripts.restore_operator_backup snapshot.ocb /new/empty/path --deletion-ledger latest.ledger`. Целевой каталог должен отсутствовать. Скрипт не умеет перезаписывать работающую БД.
4. Проверить `calendar.sqlite3`, `archive-key.pem`, `archive-public-keys.json`, права 0600 и пути конфигурации. Подключить восстановленный volume к единственной реплике.
5. Запустить сервис, проверить `/health`, доступ исходной пары, чтение старого пользовательского ZIP и только будущие напоминания.

Каждая ежедневная копия проходит пробное offline-восстановление. Автоматические тесты дополнительно поднимают Service/Backups на восстановленной синтетической БД и проверяют старую подпись ZIP. Восстановление производственного volume с реальным переключением инфраструктуры не выполняется на рабочем календаре.

## Подписи пользовательских ZIP

Ed25519 private key создаётся эксклюзивно с правами 0600 и остаётся на `/data`. Доверенные публичные ключи берутся только из серверного реестра, не из архива. Подписанный manifest содержит версию, key ID и SHA-256 payload; payload фиксирует календарь и исходную пару. При плановой ротации сохранить старые публичные ключи бессрочно, пока обещана проверяемость архивов. Удаление календаря не удаляет общие ключи. Компрометация ключа требует отдельной операторской процедуры отзыва.

Пользовательские ZIP подписаны, но не зашифрованы: скачанный файл содержит личную историю и находится под контролем пользователя. Провайдерских секретов в них нет. Нельзя восстановить архив в другой календарь или другой парой. Предпросмотр — одноразовый, 15 минут, привязан к пользователю и версии данных.

## Перевод

Приватный LibreTranslate RU/EN внутри проекта, без публичного домена. `TRANSLATION_URL` разрешает HTTPS или HTTP только в `*.railway.internal`. События, категории и текстовые исключения серии попадают в постоянную очередь. Ручные переводы не заменяются без явного разрешения; изменение исходного текста помечает их устаревшими. Ошибки повторяются с backoff, в том числе после четырёх неудач. Проверка revision предотвращает потерю конкурентной правки. Пустые поля перевода категории не считаются ручным переводом.

## Безопасность и ограничения

Проверяются подпись и свежесть Telegram initData. Сессия хранится только в памяти frontend. Права, принадлежность календарю и состояние участника проверяются на сервере для каждой операции. Приглашение непредсказуемое, одноразовое, приём атомарный. Origin/CSP/HTTPS защищают поверхность приложения; пользовательский HTML не исполняется. Webhook требует отдельный секрет и защищён от повторов. Access log отключён. Request stream ограничен по фактическому объёму, включая запрос без Content-Length.

Инженерные лимиты: сессия/свежесть initData — час; ZIP до 10 MiB и 40 MiB распакованного содержимого; операторский snapshot до 128 MiB; диапазон выдачи 370 дней, до 2000 экземпляров; 120 API-запросов/минуту на IP и путь. Эти значения не меняют продуктовые правила. Самостоятельная проверка не равнозначна независимому security audit или юридической оценке соответствия GDPR.

Google/iCloud и внешние операции остаются отключены. Пилотные адаптеры не соединены с пользовательскими аккаунтами.

## Публикация и откат 0.3.0

Предыдущая рабочая версия: commit `83d40cb947f862d6647fc57782204fdb290184b7`, Railway deployment `45524bf2-64a6-4c8f-8955-9f92de41e2a7`. Ветка `rollback/pre-0.3.0-20261016` сохраняет этот код.

При `RELEASE_CHECKPOINT_REQUIRED=true` процесс до создания приложения и запуска workers делает SQLite backup базы и копирует ключи в `/data/release-checkpoints/`. Затем шифрует checkpoint, отправляет в отдельный bucket, скачивает и пробно восстанавливает. Только после успеха запускается приложение; при ошибке запуск прекращается без изменения событий. Сохраняются три локальных точки и обычные удалённые копии по 7-дневной политике. `/health.release_checkpoint` подтверждает успешное прохождение. Healthcheck timeout для этой процедуры — 180 секунд.

Откат кода выполняется возвратом предыдущего Railway deployment либо revert merge-коммита и повторной публикацией. Код 0.3.0 не вводит миграций существующих таблиц событий; новая служебная информация находится в runtime. Откат кода сохраняет текущие события. Восстановление данных — отдельное осознанное действие: оно может убрать изменения после checkpoint, поэтому не выполняется автоматически при обычном откате интерфейса. Восстановление из удалённой копии требует актуальный журнал удалений.
