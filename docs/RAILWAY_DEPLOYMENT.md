## Telegram ID: конфигурация и безопасный перенос

В сервисе **our-calendar**, среда **production**, обязательны `TELEGRAM_OWNER_ID` и
`TELEGRAM_PARTNER_ID`. Значения задаются только в **Variables**. Оба — разные
положительные десятичные целые числа от 1 до `2^52 − 1`, без знака и пробелов.
Граница соответствует [Telegram User.id](https://core.telegram.org/bots/api#user).
Настоящие значения не добавлять в файлы, команды в отчётах или клиентский код.

`Config.env()` читает окружение один раз при запуске; `Config` централизованно
проверяет формат, диапазон и различие. Ошибки называют переменную, но не значение.
В production неполная/неверная конфигурация останавливает запуск до открытия БД.
При включённом `SETUP_MODE` отсутствующая конфигурация оставляет только прежнюю
закрытую страницу настройки, без API календаря. Подпись/свежесть Telegram initData,
подписанные сессии и проверки членства остаются обязательными.

Переменные — серверный whitelist, а не команда создания или замены пары.
Имена OWNER/PARTNER не задают порядок слотов: любой из разрешённых участников
может создать календарь, другой принимает его одноразовое приглашение.
`calendars.first_id/second_id`, `members.user_id`, получатели outbox и ID в
подписанных ZIP — данные, необходимые для существующей архитектуры.
Они не заменяются значениями окружения. Клиент получает прежние данные своего
календаря; whitelist и его конфигурация не публикуются через `/api/config`.

При первом production-запуске новая версия сверяет whitelist с календарями,
членством и ожидающими ZIP-восстановлениями, связанными хотя бы с одним из двух
разрешённых аккаунтов, затем сохраняет привязку
в `runtime.telegram_pair` в той же SQLite. Несовпадение останавливает запуск
без изменения записей. Привязка переживает окончательное удаление календаря:
изменение переменных не открывает место третьему аккаунту и не меняет пару ZIP.
Перестановка двух значений допустима и не меняет слоты. Не удалять привязку ради
смены участников; вместо этого исправить переменные на исходные аккаунты.

Другие логические календари, если они сохранились в той же SQLite от прежнего
использования, остаются нетронутыми и недоступными через whitelist. Они не
становятся участниками текущей пары. При первой привязке непустая БД без
какой-либо связи с настроенными аккаунтами отклоняется; после привязки смена
переменных на другую сохранённую пару тоже отклоняется. Посторонний member в
календаре разрешённой пары блокирует запуск.

Порядок выпуска:

1. В Railway → **our-calendar → production → our-calendar → Variables** добавить
   обе переменные с ID первоначальных участников, сверенными с действующей парой.
2. Применить эти изменения **до** публикации версии, требующей переменных.
   Если видна кнопка Deploy для staged changes, переменные ещё не применены.
   Их применение может перезапустить прежний код; это совместимый первый шаг.
3. После успешного CI выпустить код через существующий GitHub `main` → Railway.
   Не менять `DATABASE_PATH`, `/data`, volume, signing keys, Google/iCloud tokens,
   `DEMO_MODE` или число реплик. Резервный release checkpoint остаётся обязательным
   там, где включён `RELEASE_CHECKPOINT_REQUIRED`.
4. Дождаться Railway `SUCCESS` и `/health` с `ready=true`, `demo=false`.
   При ошибке пары исправить переменные, не редактировать участников или БД.
5. Оба участника проверяют открытие Mini App со своих Telegram-аккаунтов.
   Производственные удаление/восстановление и тестовые сообщения не запускать.

Прежний явно включаемый локальный `DEMO_MODE=true` сохранён для синтетических
тестов: он может работать без обеих переменных. Это не fallback при ошибке
production-конфигурации; production сам в demo не переключается.

Аудит исходного main от 19 октября: персональные константы находились только в
`app/security.py` и `tests/test_access_whitelist.py`. Во frontend, документации,
скриптах и миграциях их дубликатов не найдено. Git-история содержит старые значения
(в том числе коммиты `afb1b17`, `4709250`, `7cdceff`); история не переписывалась.
В актуальном коде используются окружение, данные SQLite и проверенные Telegram
updates/initData. Права администратора для третьих лиц не добавлены.

## Что нужно владельцу

1. В BotFather выбрать `/mybots` → `@ourcalendar_bot` → Bot Settings → Configure Mini App и включить основную Mini App с URL `https://our-calendar-production-ffcb.up.railway.app`.
2. Открыть https://t.me/ourcalendar_bot, нажать Start, затем кнопку календаря. Каждый участник должен нажать Start в чате с ботом.
3. Пройти docs/RELEASE_CHECKLIST.md на двух настоящих аккаунтах, включая напоминание при закрытом Mini App.

До заполнения переменных сервер показывает только закрытую страницу настройки. `SETUP_MODE=true` не включает демоданные и не обходит Telegram authentication. После заполнения конфигурации обычное приложение выбирается автоматически. Сервис настраивает webhook/menu после проверки соответствия token и username.

Legacy Config as Code (`railway.json`) не поддерживается для новых сервисов Railway. Параметры выше заданы через Railway API, файл из репозитория удалён. Для будущей декларативной конфигурации можно импортировать существующие ресурсы через Railway IaC без включения значений секретов в source.
